# Iteration 0.4.0 — live task list refresh and card UI

Frontend experience iteration after 0.3.0 (high-tier quality and robustness hardening): fix progress not refreshing, SSE connection-count limit, two-state task card layout.

## Changes

- `currentTab` state out of sync | only `onShadowClick` updates it, `renderTab("tasks")` (auto-jump after starting a download) does not → `renderTab` maintains `currentTab` uniformly | when auto-switching to the task list after starting a download, `currentTab` is still build, so the `updateCard` guard `if (currentTab !== "tasks") return` blocks all SSE/polling DOM updates, progress stuck at 0% until the tab is switched manually
- SSE channel | one `/api/jobs/{id}/stream` per job (EventSource×N) → single global `/api/jobs/stream` (events carry job_id) | Chrome caps HTTP/1.1 concurrent connections per host at 6, later SSE connections queue up and fail once there are many jobs; the global stream always occupies only 1 connection
- Polling fallback | per-job 2s `GET /api/jobs/{id}` → global 2s full `GET /api/jobs` | symmetric with the global SSE, also a single connection; add/remove of jobs during disconnects stays synced too
- Event naming | `done` / `error` terminal states → unified `status` (carries `status/out_path/error`) | `error` conflicts with the EventSource network-layer event name; the frontend `addEventListener("error")` would be consumed by network errors
- Task card | fixed full card (always shows `out_path`) → **mini/full two-state** (default mini, click the title row/"expand" to switch to full showing path and error) | `out_path` is very long, a few jobs fill the floating panel; mini is the high-frequency state, full reserved for details and future features
- Historical job progress | db-returned rows always have `percent` 0 → when no in-memory state, fill in by status (done=100%) + frontend `done` fallback 100% | after backend restart, completed job list showed 0.0% and empty progress bars — an illusion

## Implementation notes

- Global SSE scans the job status table every 0.5s, pushes incremental updates by `status|phase|percent|speed|eta` snapshot changes; terminal states pushed only once per connection.
- Frontend `watchAll()` maintains a singleton SSE + full polling; `closeAllWatchers` closes old streams then rebuilds.
- Expanded state `expandedJobs` (memory-level, remembered per job); `outerHTML` redraw is driven by `jobCard`, progress refresh does not lose the expanded state.
- Verification: `uv run ruff check backend/`, `node --check userscript/bilibili-download.user.js` passed.

## TODO / rollback notes

- `/api/jobs/{id}/stream` kept for compatibility (old frontends work), can be removed later.
- mini/full expanded state not persisted (GM_setValue): refresh returns to default mini; cross-session memory can be added later if needed.
- The global SSE pushes a full snapshot on initial connection, so the first frame has many events with a large job count; the current list cap is 200, no practical impact.
