# Iteration 1.4.0 — format_id-bound quality pipeline (display-only frontend)

## Changes

| Topic | Before → After | Reason |
|-------|----------------|--------|
| Tier labels | legacy height labels built by the backend (`1080P60`/`720P`) → **yt-dlp's own display names** (`4K 超高清`, `HDR 真彩`) | the old height-fallback mislabeled qn=120 vs qn=125 as "two 4K" (the yt-dlp bilibili extractor reports both as 2160p); showing the extractor's `format` string is the only honest label and collapses the duplicate |
| Codec selection | frontend picked a format_id from a per-tier `format_ids` dict (codec-family logic in JS) → **backend binds one `format_id` per tier** at `/api/info` time using the user's `codec` preference (`bind_qualities` + `_FORMAT_TABLE`) | the frontend is display-only: the user's codec/video preference is sent to the backend, which resolves the concrete yt-dlp stream per tier; the panel just renders and passes the id back |
| Download format expression | height-based `-f` chain from `quality` (as a legacy label) → **`{format_id}+bestaudio` with a `/`-fallback** to the height+codec expression recorded at probe time, then `best` | bilibili format_ids are stable per (qn, codec) across a season but individual episodes can differ (verified: ep374622 swaps a hev1 1080P id `30102` vs `100143` on the other eps); the fallback keeps whole-season batch downloads working when one episode lacks the exact id |
| Format_id fallback table | n/a → process-level `_FORMAT_TABLE: {format_id → height+codec fallback}` populated by `bind_qualities`, carried into each job's `params.format_fallback` | `format_id` itself does not encode resolution/codec; the table records them from the same yt-dlp format object that yielded the id so the `/`-fallback can reuse the identical parameters |
| API contract | `/api/info` took only `url`+`cookies`; tiers exposed `codecs`/`format_ids`; `/api/download` took `format` → now `/api/info` takes `codec`, tiers expose `{qn,label,format_id,codec,size}`; download takes `format_id` | field name unified to `format_id` across frontend/backend; the bound stream is a single id, not a dict to resolve client-side |
| Codec identity | family aliasing (`hev1→hvc`, filter `[vcodec*=hvc]` mapped back to `hev1`) → **literal yt-dlp vcodec prefixes** (`hev1`/`hvc1`/`av01`/`avc1`) everywhere: `normalize_codec_order`, `codec_family`, the `[vcodec*=...]` filters, the settings dropdown values, and the `codec` field | no mapping table to keep in sync; bilibili reports both HEVC spellings (`hev1` for DASH, `hvc1` for HDR/qn=125), so the default order lists both; codec preference in frontend/backend/docs is just yt-dlp's own strings |
| defaultQuality setting | settings panel had a "Default quality" dropdown persisted in GM_setValue → **removed** | per decision, the default selection is simply the highest tier (first button = `Auto`); it added a mapping that the format_id pipeline no longer needs |
| Tests | 58 cases → **66** (bind_qualities selection/table/overwrite + _download_format priority/fallback/audio/legacy) | the format binding and fallback are the new core logic and must be unit-tested without network access |

## Implementation notes

- Verified with a real logged-in cookie: `ss1733` episodes share the same format_id per (qn, codec) — e.g. qn=120 avc1/hev1/av01 = `100035`/`100036`/`100241`, qn=125 = `30125` (hvc1, HDR) — except one hev1 1080P id on ep374622; that exception is exactly why the `/`-fallback exists.
- `bind_qualities` runs after the probe cache read (cache key stays `(url, logged_in)`), so the codec preference does not fragment the cache.
- `_download_format(state)`: `format_id` present and not audio → `f"{id}+bestaudio/{fallback}/best"` (or `f"{id}+bestaudio/best"` when the fallback is missing); audio → `bestaudio`; otherwise the legacy `quality_to_format` chain (still used by `auto`/older requests).
- The userscript `fetchInfo` now sends `codec: getCfg().codecPref || "auto"`; the download payload drops the old `format` field in favor of `format_id` (empty for `auto`/`audio`).

## TODO / rollback notes

- Rollback: restore `_download_format` to `quality_to_format`'s chain, drop `bind_qualities`/`_FORMAT_TABLE` from `/api/info`/`/api/download`, and revert the userscript quality-button dataset to height labels; the probe/bangumi behavior is unchanged.
- Not covered: a format_id bound from the sampled first episode is only validated against `_FORMAT_TABLE` (same probe session). If a download is submitted for a never-probed episode, the fallback record is missing and the expression degrades to `{id}+bestaudio/best` — safe but not height-guaranteed.
