# Iteration 1.2.0 — Multi-arch image (amd64 + arm64) + digest versioned tags

## Changes

| Topic | Before → After | Reason |
|-------|----------------|--------|
| Published platforms | `linux/amd64` only → `linux/amd64` + `linux/arm64` multi-arch manifest | Apple Silicon (Mac M-series) and arm64 hosts could not run the image natively; buildx + QEMU (setup-qemu-action) cross-builds the arm64 layers on the amd64 runner, docker pull hands each host its native architecture |
| CI version tag | hardcoded `1.1.0` in the workflow → read from `pyproject.toml` at build time | the tag must match the app version without editing the workflow on every bump; one source of truth for `version` |
| Base environments | python:3.14-slim + uv:latest images + all pinned wheels (imageio-ffmpeg ships `manylinux2014_aarch64`) already multi-arch | no Dockerfile changes needed; yt-dlp/uvicorn/pydantic are pure-python or ship arm64 wheels |
| compose default tag | `1.1.0` → `1.2.0` | `docker compose up -d` now points at the multi-arch release |

## Implementation notes

- `docker/setup-qemu-action@v3` runs **before** buildx so the binfmt handlers are registered for the arm64 build; the publish job only runs on `main` pushes (not PRs).
- Verified against the published manifest: `docker manifest inspect` shows distinct `linux/amd64` and `linux/arm64` platform entries under the same `1.2.0` tag.
- No local re-verification of the arm64 runtime yet — needs a real Apple Silicon/arm64 machine.
